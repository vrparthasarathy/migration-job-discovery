# Requirements: Client Transfer Package

The shared rules are in the [root requirements](../requirements.md#requirements).

## Requirements

- Goal: one text-only zip, `AIRO-Client-Transfer.zip`, that can be sent into the client environment and restored there by Copilot Agent mode, with the completed skills, contract, guides and lead tools in their original relative layout.
- Every zip member ends in `.txt`. A payload file is stored as `payload/<original path>.txt` with its bytes unchanged. Generated text files sit at the zip root.
- No hashes (user decision, 2026-11-16, to save time). Integrity rests on the byte size in the manifest, the zip's own per-member CRC, and the byte-for-byte comparison of `verify` against the source files. Adding hashes later is a manifest field and one check.
- The payload is a data file, `payload.txt`, one path or glob per line (comments start with `#`), so the contents change without code changes. Exclusion rules are code: git data, hidden files and folders, `node_modules`, caches (`__pycache__`, `.craft`), `.env` and key files, generated output, and component records (`craft.json`, `tasks.md`, `README.md`, `requirements.md`, `contract.md`, `review-checklist.md`, `changelog.md`, `backlog.md`). No component record is needed at run time, and none is packed, so the pack carries no internal process term.
- A secret-like value in any payload file stops the build. The scan reuses the idea of the Tracker Reconciler's `secrets.ts`, applied to bytes read as text.
- Replacement of existing skills is accepted by the user: Copilot installs the skill folders into `.github/skills` replacing existing copies of the same skills and lists what it replaced. Other files that differ are flagged before overwriting and identical files are left alone. `AGENTS.md` and unrelated configuration are never replaced.
- Local checks never claim Copilot skill discovery or client use cases are validated. The package says Copilot throughout.
- No email is created or sent by this component.

## Payload (first draft; edit `payload.txt` to change it)

- Skill folders, complete: `copilot-drafting-guide/document-job-behavior/`, `identity-access-discovery/discover-identity-access/`, `tracker-update-proposer/propose-tracker-updates/`, `workflow-recommender/recommend-workflows/`, `discovery-orchestrator/run-discovery/`.
- Contract and guides: `tracker-data-contract/tracker-data-contract.md`, `tracker-schema.csv`, `tracker-updates-template.csv`, `use-case-inventory-template.csv`, `workbook-layout-guide.md`; `copilot-drafting-guide/usage-and-model-guidance.md` and `drafting-prompt.md`; `job-behavior-template/job-behavior-template.md` and `filling-guide.md`; `website-check-job-behavior/website-availability-check.md`.
- Tools with their `package.json`, `src/`, `test/` and fixtures: `tracker-tools/tracker-tables`, `tracker-reconciler`, `tracker-summary`, `review-csv-exporter` (with `data/review-headings.csv`).
- Root integration tests: `test/*.ts`, with the files they read (the template, the reference specification, the skill folders and the contract files above, and the tools' `src/cli.ts`).
- The process guide is generated at build time from the end-to-end handoffs table of the root `contract.md`, because that file mentions internal process terms and is not packed.
- Not packed: the Website Availability Check source (no test reads it), all component records, and the Sample Tracker Workbook (a team-review sample that needs a network `npm ci` for `exceljs` and carries a generated `.xlsx` binary; no client runtime need). To include its sources and data, add `tracker-tools/sample-tracker-workbook/{src,data,test}/**`, `package.json` and `package-lock.json` to `payload.txt`, and leave the `.xlsx` out (it is regenerated by `npm run generate`). It is the one essential binary the sample would otherwise need, and the quickstart says so.

## Must match the source

- Each payload file's bytes, and the layout the root tests rely on: tools import each other and read `tracker-data-contract/tracker-schema.csv` by relative path, and the root tests walk the whole tree, so the tree must be restored into one folder whose only copies of the contract and schema are the five the root test expects.
- The commands in `CLIENT-QUICKSTART.md.txt`, which `build` checks against the packaged files (the scripts and entry points it names must exist in the manifest).

## Need not match

- Hashes, signatures, an installer, automatic skill discovery, any email step, and the Sample Tracker Workbook's `.xlsx`.

## Technology

- Python 3.9 or later with the standard library only (`zipfile`, `json`, `subprocess`, `argparse`, `unittest`), no packages, so the same language builds the package and ships the restore script the client runs. This departs from the project's Node 26 stack because Node has no built-in zip writer and the client restore must be Python; to use Node instead, replace `package.py` and `restore.py` and ship a Node restore script. The packaged tools still need Node 26 on the client.

## Follow-on work (recorded, not built)

- A dedicated team process guide document instead of the generated one.
