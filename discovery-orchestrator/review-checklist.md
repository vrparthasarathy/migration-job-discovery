# Review Checklist

Internal review of the `run-discovery/` skill folder. Not sent to anyone. Use it as a reviewer who has not seen the folder before. Mark each item pass or fail. This is the stand-in for automated checks; no tool runs it. Every item stays unticked until a fresh review passes it.

Testing policy: behaviors are checked by reading the files and by manual testing in the client environment on real use cases, recorded against the version they cover. No Copilot run has been made for this folder, and nothing here claims one. Items that need a real run say so.

- [ ] [B01] `SKILL.md` has the skill state the use case, its vendor and source location read from the folder, and the four stages in order (source screening, identity and access, behavior documentation, workflow recommendation) before it runs them. Needs a real run to confirm what Copilot does.
- [ ] [B02] `SKILL.md` runs the stages one after another through `propose-tracker-updates` (source screening), `discover-identity-access`, `document-job-behavior` then `propose-tracker-updates` (specification update), and `recommend-workflows`, each writing only its own rows in its own file, and writes no proposal file itself.
- [ ] [B03] `SKILL.md` asks once, in one message, for the proposal ID, the vendor and source location when absent, the recommendations proposal ID, the export folder, the proposals root, the exporter path, output folder, the lead's name and date, and never invents them or takes the name or date from the environment.
- [ ] [B04] `SKILL.md` skips stages 3 and 4 when `source_status` is `not-located` or `empty`, says why, does not skip for `uncertain-mapping`, and records the blocker through stage 1.
- [ ] [B05] `SKILL.md` runs `recommend-workflows` over every specification processed so far, taken from the Use Cases rows under the proposals root, with a lead-confirmed list and one recommendations proposal ID per session.
- [ ] [B06] `SKILL.md` runs `node <exporter path>/src/main.ts export-review --export <dir> --proposals <root> --out <dir>` (compare with the exporter's `contract.md`), stops and shows the error on exit 1, and reports per stage what was proposed, skipped or blocked, then the counts including rejected rows. The four output file names match the exporter's.
- [ ] [B07] `SKILL.md` runs only the chosen next folder, does not rerun earlier folders unless the lead asks, and says their rows stay in the review files.
- [ ] [B08] `SKILL.md` forbids writing to the tracker, releasing a question, recording an acknowledgement or a decision on its own, applying a change, editing a proposal file or another skill's output.
- [ ] [B09] `SKILL.md` walks pending rows (blank `review_status` or `changed_since_review` = `yes`) in the `order` column, found through the headings file keys (every key named exists in `tracker-tools/review-csv-exporter/data/review-headings.csv`), shows use case, record, kind, per-field current, proposed and state, conflict, suggestions, evidence and reason, records accept, reject or clarify only from the lead's words in `review_status`, `reviewer`, `review_note` and `reviewed_on` of that row, sets `applied_on` only on a date the lead gives after hand-applying, asks again when unclear, and reruns the exporter after recording.
- [ ] [B10] `SKILL.md` accepts all of one use case's plain `add` rows with no conflict and no held change, in the lead's name, in one step, touches no other row, and lists rows recorded and rows left.
- [ ] [Rules] The folder holds only `SKILL.md`, front matter `name: run-discovery` equal to the folder name, a description with trigger phrases, `user-invocable: true`. Wording scan: no Craft term, command or file (`craft`, `task`, `acceptance`, `component`, `README`, `contract.md`, `requirements.md`, `/craft:`), `use case` for the business unit, `job` or `script` only for the vendor's script, no secret, no real vendor data.
