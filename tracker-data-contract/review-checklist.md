# Review Checklist

Internal dry-run review of `tracker-data-contract.md`, `tracker-schema.csv`, `workbook-layout-guide.md`, `tracker-updates-template.csv` and `use-case-inventory-template.csv`. Use it as a fresh reader who has not seen them before. Mark each item pass or fail. This is the stand-in for automated checks; no tool runs it. Items stay unticked until a fresh review passes them.

- [ ] [B01] Every column in the contract's Tabs and columns table has exactly one row in `tracker-schema.csv` with tab, column, key flag, owner class (spec, human, forbidden or computed), visibility (V or I), type (text, date, ref, enum, list or url) and allowed values for every enum; every tab has at least one key; no row is duplicated.
- [ ] [B02] The References table gives the central scheme (`UC-###`, `QN-####` per use case and question, `QG-###`, `QL-####`, `MP-###`, `AX-###` per use case and endpoint, `BT-###`, `WD-###`) with the rule that only leads assign them, and the local references used in proposals; a proposal carries no central reference for a new row.
- [ ] [B03] Every status list is defined with its meaning: use case stage and source status, grouping impact, question status (open versus resolved), the vendor's answer status, mapping status, access request status, authentication type, verification and batch status; behavior acknowledgement, access approval or provisioning, and verified access are separate fields that are never combined.
- [ ] [B04] Captured and released are separate; the due date is release plus two working days per row, never reset by a response or a resolver, and absent before release; the overdue rule covers open rows that are not completely answered or are in clarification-requested; partial and cannot-answer rows stay open and overdue and are also follow-ups; a complete answer awaiting lead review is not vendor-overdue and shows its owner and age.
- [ ] [B05] The proposal file defines encoding, the twelve columns, the operations (add, set, link, suggest), the composed `update_id`, the location and which skill owns which tab, the four owner classes, and that every row traces to a specification, to inventory or source-screening evidence or to dependency evidence; the header of `tracker-updates-template.csv` equals the column list; a proposal never releases or applies anything.
- [ ] [B06] The export is one CSV per tab with the schema's column names plus `manifest.csv` (scope, workbook, exported_at, exported_by); dates are `YYYY-MM-DD`, multi-value fields are `;`-separated, and extra lead columns are allowed and preserved.
- [ ] [B07] The vendor-view rule appears in the contract and the guide: only that vendor's rows and V columns, question rows only after release with no group, link or other-row reference, no mapping or cross-vendor information, no hidden tabs or columns, and no secret value; the vendor workbook has no Batches, Question Groups, Question Links or Mappings tab.
- [ ] [B08] A question that concerns several use cases is several rows, each with its own answer and answer status; grouping is internal; no answer is copied to or inherited by another row; a new or newly linked row starts blank; the guide's copy steps never copy an answer across rows.
- [ ] [B09] `workbook-layout-guide.md` gives the tabs, the vendor's single Questions sheet, the drop-down lists, the vendor-view rule, the due-date formula (release plus two working days), the manual vendor-to-master copy steps, the manual apply steps for the reconciler's output, separate vendor access as a deployment prerequisite with the storage choice deferred to the client, and the inventory template; `use-case-inventory-template.csv` is header-only with `use_case_name,vendor,source_ref`.
- [ ] [B10] None of the five files contains an internal build-process term, real vendor data or a secret value (the hygiene scan finds none).
