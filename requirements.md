# Requirements

## Requirements

- The project delivers two things. The first is the job behavior pack for vendor review: a blank template, a short filling guide, a completed reference specification of the website-check use case, and a GitHub Copilot agent skill with usage guidance and a fallback prompt. The second is the use case tracker toolkit: one shared tracker data contract, three Copilot skills (tracker updates, identity and access discovery, workflow recommendations) and the lead tools (a table library, a reconciler and a daily summary). Our team's developers use GitHub Copilot (VS Code agent mode) and no Craft; leads run the tools by hand with Node.
- Real, separate vendor access and internal-only analysis are an intake and deployment prerequisite, settled before the first release to a vendor and not an implementation blocker; the vendor storage and repository choice is deferred pending the client's confirmation.
- Audiences stay separate. The vendor receives only its own finished specifications, read through a GitHub link, and its own vendor workbook (its use cases, released questions, answers, acknowledgement and access requests). Everything else is internal: the skills, the contract, proposals, the reconciler and summary output, recommendations, lead decisions, the master workbook and any cross-vendor comparison.
- The pack is plain Markdown files and skill folders: `job-behavior-template.md`, `filling-guide.md`, `website-availability-check.md`, the skill folders, `usage-and-model-guidance.md` and the fallback `drafting-prompt.md`, plus the contract Markdown and CSV files. No Craft installation, file, command or term is needed or mentioned in them. The `README.md`, `craft.json`, `tasks.md`, `requirements.md`, `contract.md`, `backlog.md` and `review-checklist.md` files are internal and are never sent.
- Vocabulary: a use case is what the business needs done and carries the vendor's own name, and the vendor with that name is its identity, written as its use case ID (`uc-<vendor-slug>-<use-case-slug>`, defined once in the Tracker Data Contract); a script is the vendor's current implementation; a workflow is one reusable implementation on our platform that supports several use cases through configuration. Team-facing documents, tracker tabs and outputs say `use case`. Vendor-readable text never mentions workflows or grouping. Existing folder, file and skill names are not blindly renamed (see the backlog item `use-case-naming-alignment`).
- Purpose of the specification: the vendor, who runs and maintains the use cases today, reviews and acknowledges a versioned record of each use case's current behavior before our team migrates it onto our client's platform. The record protects against scope creep and outdated scripts: it shows what the vendor acknowledged, for which script. This is an as-is migration, so there are no requested changes and no approved items.
- Two kinds of statement stay separate: current behaviors (`B1`, ...) and questions (`Q1`, ...). A question is asked only when the source cannot show the answer and the answer would change what the migrated use case must do; it is never about what the source states or the reason behind a behavior the source shows. Every question traces to a specification question (its ID and version). Existing findings, questions, corrections and dependency observations that developers supply are structured into the specification by the drafting skill and then proposed, so nobody rewrites them first and no free-standing intake exists. Current source behavior, unanswered questions and supplied vendor answers stay distinguishable, and statements are kept as source-observed, document-described, team analysis or inference, and recommendation.
- The core inputs are the source code and the exact files `external_tools.md` and `logic.md`; additional documents (original SOPs, vendor documents) are tagged manually. Existing analyses are starting inputs, not verified or approved baselines, and evidence is checked for support with conflicts flagged and not guessed. The skills support first generation and repeatable updates from existing findings, preserving IDs, history and human decisions and creating no duplicate records.
- The three skills have separate roles: the drafting skill structures and verifies source, `external_tools.md`, `logic.md`, supplied findings and tagged documents into the specification; the access skill proposes access rows per use case and endpoint with no specification; the tracker update skill has a source-screening mode upfront and a specification-update mode later. Source screening and access discovery may run in parallel before specifications exist, while leads review and raise ready requests as drafting proceeds.
- Missing, empty or unlocated source is flagged upfront for the whole inventory, before any specification exists and from inventory or source-screening evidence, as a discovery blocker with a responsible owner or `unassigned`, kept distinct from confirmed unavailable and uncertain mapping, and shown in the summaries; available documents never clear it.
- One file per use case with a change log and no job ID; the use case name is the identity and file name. Our team tags the repository at each acknowledgement.
- Acknowledgement is recorded by our team from the vendor's tracker entry or reply, and is never inferred. It is never described as preventing all future issues, and inferred behavior is never presented as current behavior or as approved. Behavior acknowledgement and verified access readiness are separate signals.
- One tracker data contract serves every skill and tool. The authoritative tracker is Excel on SharePoint: one internal master workbook and vendor-specific workbooks. Proposals (`tracker-updates.csv`) stay outside it until a lead reviews them; leads copy vendor answers into the master and apply reconciler output by hand. Direct integration is deferred.
- Questions arrive incrementally from developer merge requests. The vendor sees one row per use case per question on one simple Questions sheet, each with its own answer and status; shared grouping and links stay internal, and no answer is inherited by a newly linked or newly added row. Minor wording edits keep a question's identity; a possible change of meaning is flagged for a lead with earlier answers preserved, and a lead decides any replacement. Capture and release are separate: a vendor's two-working-day due date starts at release, and overdue questions go on the daily call from day three. A response is not a resolution: a partial answer stays open with its original due date, a cannot-answer row stays open until a lead assigns a resolver or closes it, neither resets the deadline or leaves overdue visibility, and follow-up and overdue can both apply. A complete answer awaiting lead review is not vendor-overdue and shows its owner and age, while a lead-requested clarification stays open on its original due date and can be overdue even when the vendor's `answer_status` is complete; the vendor owns `answer_status` and the lead owns `status`. Whether vendors get a `same as` shortcut is undecided.
- Mappings: specifications are drafted across the whole use case set, recommendations are generated incrementally over the full set without waiting for acknowledgement, and leads decide mappings (accepted, rejected or pending-clarification, with rationale, evidence, versions, date and decided-by name). Similarity is behavior-based, never a primary filter on shared systems. No persistent per-use-case profile files are kept, the method is never claimed proven, and unread or missing specifications are shown. Grouping impact is assessed separately from behavior change, with a short reason and a lead override: a change that could affect grouping, or whose impact is unknown (never treated as no impact), may suggest re-review and never overturns a decision; a version bump, a spelling edit or a behavior change with no grouping impact does not, and a rejected pairing needs new evidence. Earlier workflow analyses tagged by a lead supply candidates only. Cross-vendor recommendations stay internal and each vendor confirms only its own scope.
- Identity and access discovery runs from day one as an early lightweight sweep across all known use cases, in parallel with behavior discovery, on source, configuration and the core files. It records rows per use case and endpoint with environment, observed operations, exact identity or variable references (runtime values unknown), evidence, and unknowns with a resolver, never a secret, and never an invented permission, request, approval or availability fact. Request wording follows the observed authentication (a website sign-in or an API). Identical endpoints are only flagged for lead review, and leads may consolidate while keeping per-use-case traceability; sufficiently defined requests are raised promptly while other unknowns are resolved. Approval or provisioning, verified working access and behavior acknowledgement are separate signals.
- Trial limits per vendor (one candidate workflow group, about 3 to 5 use cases, about 5 distinct questions, around three vendor tracks) are provisional, entered by leads and adjusted from the backlog and actual turnaround. The real inventory per vendor is not known and no distribution is invented.
- Document and skill components are not run by any tool; verification is each component's `review-checklist.md` file review, and each behavior carries the `untested: benchmark pending` marker. At the root, the plain file comparisons (the template, specification and skill copy; the contract and schema copies) are also run by `test/documents.test.ts`, so root `B01` and `B05` carry no marker; root `B02` to `B04` rest on the root `review-checklist.md` file review and scans and keep it. Testing policy (user decision, 2026-11-15): a revised skill or guide does not require a fresh Copilot dry run on the website reference. The user tests each skill manually in the client environment on real jobs or use cases, gives feedback in ChatGPT, and the skill is iterated. Reported results are recorded as user-reported evidence labelled with the version they cover, and no pass is claimed for a revised version until the user reports one. The file-reading review checklist still applies. Code-tool tests (`tracker-tools` and the root integration test in `test/`, which runs the built tools through their `cli` modules in real temporary directories on the real example proposal and schema) are not waived. The tools are code with real tests. Document and skill components declare an empty `checks` so they do not inherit the root's integration `test` check.
- The illustrative job [Website Availability Check](website-availability-check/README.md#purpose) stays unchanged and read-only as source evidence. It declares its own `test` and `coverage` checks, which no document component uses.

## Must match the source

- Not applicable for the documents beyond what each component states. The reference specification must match the behavior of the illustrative job's source.
- The tools must implement the [Tracker Data Contract](tracker-data-contract/README.md#purpose) exactly; no column list is repeated in code.

## Need not match

- Broader network connectivity, environment setup and router availability: an open, deferred scope pending a developer sample sheet, and not authorized scope.
- Any implementation of a use case on the migration platform, or the real grouping decisions.
- Excel or SharePoint file internals, or any real vendor data.
